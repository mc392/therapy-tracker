# Test data — eight synthetic practices

Eight complete GroundWork practices, as **importable backup files**. Every one is a real backup
envelope (the same shape `backupPayload()` writes), so any of them can be restored on a device
through **Settings › Data & backup › Restore**, and read straight off disk by the review harness.

**There is no real data here.** Client codes are synthetic (`C101`, `PT3`, `S214`), there are no
names, and nothing clinical: the `notes` field on a session is the app's yes/no "written up"
marker, not a note. Generated by `scripts/make-test-data.mjs`, which is deterministic — running it
again reproduces the same files byte for byte.

## The eight

| File | Practice | Size | Basis | What it is for |
|---|---|---|---|---|
| `…-day-one.json` | one client, one session, two days in | 1 session | cash | the floor — every engine has to survive it |
| `…-newcomer.json` | three months in, works at home | 42 sessions, 4 clients | cash | the readiness gates: most trends should decline politely, and the tax disclaimer is **not** yet acknowledged |
| `…-online-only.json` | online only, 17 months, most features switched off | 257 sessions, 11 clients | cash | simple reveal mode — Money and Tax are off, so the tabs fall back |
| `…-part-time.json` | ~£4.6k profit, under the personal allowance | 272 sessions, 6 clients | **accruals** | no income tax, no Class 4, Class 2 paid **voluntarily**, use of home at the £18 band |
| `…-chaotic-payments.json` | untidy: a third never paid, tick-list barely used | 419 sessions, 14 clients | **accruals** | cancellations at 0/50/75/100%, badly overdue clients, no referral sources |
| `…-established.json` | four years, room hired **per session** | 1,183 sessions, 27 clients | cash | the volume case: a fee rise mid-history, a room rate rise, holidays, a client discharged last week |
| `…-winding-down.json` | five and a half years, 28 of 30 clients finished | 1,425 sessions, 30 clients | cash | a practice mostly in the past — seven tax years |
| `…-scotland-high.json` | ~£54k profit in Scotland, monthly room rent | 1,515 sessions, 30 clients | cash | Scottish bands, Plan 2 student loan **ending** 2026-27, a pension, two filed years with HMRC's own figures, instalments HMRC set, and a claim to reduce (SA303) |

`index.json` lists the same thing in machine-readable form.

## Anchored to a date

Everything is built around **`ANCHOR = 2026-09-05`** — "fourteen months ago" is resolved at
generation time and written out as an absolute date, so the files are stable and diff cleanly.

The engines, though, read the real clock: last 12 months, last 26 weeks, this tax year. Once the
real date has moved on by a season the fixtures stop landing in those windows, and the trends
gates start reporting on data that has aged out. **Re-run `npm run testdata`** when that happens —
it is deterministic, so nothing but the dates moves. The same caveat applies to
`tests/tax-tests.js`, which assumes 2026-27 is the year in progress.

## What a fixture deliberately does not carry

`groundwork-testdata-scotland-high.json` assumes a **£400/month pension contribution**, and it is
not in the file. `pensionPcm()` reads `localStorage.tt_pension`, which is per-device and does not
travel in a backup — so a restore silently drops it and every tax estimate moves. The value is
recorded under `testData.device` instead, the harness applies it, and the gap is written up in
`docs/test-data-review-2026-09.md`.

## Running things against them

```bash
npm i --no-save playwright     # deliberately not a dependency — see the script headers
npm run testdata               # regenerate the eight files
npm run test:review            # run Trends + Tax over all eight, assert the invariants
npm run test:tax               # tests/tax-tests.js, headless
```

`npm run test:review` loads the real `index.html` in a browser, injects each practice, runs every
`ana*` function and the whole tax engine, renders all nineteen screens, and checks the invariants
that only show up at this size — the four MTD quarters reconciling to the year on **both** bases,
`profitBreakdown` agreeing with `tyNet`, the drifting list and the episode count matching their own
stated rules, and the cost ratio counting what `tyNet` subtracts. It exits non-zero if any fail.
